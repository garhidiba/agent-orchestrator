# Workflow

The current conversation dispatches native Agents; MCP prepares leases/worktrees and verifies Git/results. Installation readies the MCP. A native connection readies this conversation's worker relay; it is not an independent AI controller.

## Project setup

Use the installed conversation's init route before execution when project setup is requested; [project initialization](configuration.md#project-initialization) owns its root checks, full configuration and preview semantics. This config-only route starts no run or worker and requires no native connection. A complete configuration file is separate from verified native execution readiness.

## Native connection

For execution requests, complete `NEEDS_HOST_HANDSHAKE` automatically before creating a run:

1. Read `nativeHandshake` from `orch_environment`. Keep `coordinatorTokenRef` private to the parent; read that file only for authenticated MCP calls.
2. Use the active host's real native Agent tool (`spawn_agent` in Codex, `Agent` in Claude). Ask a read-only probe agent to echo the challenge and report physical cwd, Git root, branch and HEAD of `nativeHandshake.originRoot`. Obtain the native agent ID from the host tool result, not an invented role name. Await its actual result. Metadata subprocesses and shell-written fake receipts are not probes.
3. Relay that result through authenticated `orch_host_connect`: `native_tool`, `native_agent_id`, and `probe:{challenge,cwd,origin_root,branch,head}`. The receipt must match the current Git context and unexpired server challenge. Reread `orch_environment`; continue only with `nativeDispatch=READY`. This binding lasts for this MCP connection; repeat after reload/reconnect.
4. Relay optional `native_context` with actual current-host model/effort metadata and supported `perInvocationModel` / `perInvocationEffort` flags. When the callable model parameter has a finite enum, relay it separately as `invocationModelIds`; that enum is narrower than the configuration catalog. Include `models` descriptors only with actual host/API or current official host-configuration evidence, following [model selection](model-selection.md#native-metadata-for-configuration). Preserve descriptor source, timestamps and evidence. A metadata catalog or documented setting cannot establish invocation capability. Authentication and the Git challenge bind a trusted parent receipt, not signed host/account proof. Refresh actual current-context metadata with `orch_host_refresh` and a fresh physical Git `probe:{cwd,origin_root,branch,head}`; keep prior task/review receipts immutable.
5. Resolve every role from its current policy and authenticated native capabilities. Pass the prepared model and effort into the actual native invocation parameters; for Codex these are `model` and `reasoning_effort`. If its tool requires `fork_turns=none` for overrides, send the prepared handoff explicitly in that fresh context. Use the host's corresponding supported definition/invocation path for Claude. A prompt asking a worker to use another model is not parameter application. Omit unknown/inherited arguments only when the prepared policy calls for inheritance; never replace a resolved selection with `auto` or silently drop a pin. If the available host tool cannot accept the requested model/effort or required reload is unresolved, keep execution blocked. Record requested, resolved and observed separately; unknown observations stay null.

## Claude full model IDs and effort through named definitions

When Claude's current `Agent` schema cannot express the exact selected model or effort, use the PRD's generated-definition path rather than changing the user's settings. This applies to writing roles and to independent `reviewer` / `final_auditor` dispatches. Keep this conversation as coordinator; a coordinator policy does not authorize replacing it with a new AI controller.

1. Read effective role settings and `orch_models.authenticatedNative`. If a valid requested version or effort is absent from the alias-only metadata, obtain its exact support and host-version constraints from current official Claude configuration metadata/documentation. Relay that advertised configuration descriptor with authenticated `orch_host_refresh`; preserve actual invocation flags and `invocationModelIds`. Unknown access and actual backend observations stay unknown. Do not treat a documented setting as an exposed invocation parameter.
2. Call authenticated `orch_claude_role_prepare` with `role` and `expected_hash=hashes.project` from the current effective-config read. `dry_run:true` previews only. The authorized write derives a project/policy-specific `name`, writes a bounded immutable `.claude/agents/<name>.md` using the shipped role template and exact resolved model/effort, and adds only that exact generated path to local Git `info/exclude`. It never rewrites global agents, user-owned conflicting files or `.orch/config.yaml`. The returned `sha256`, `model`, `effort` and reload hint are preparation evidence, not proof the host loaded the definition.
3. Use the real current-host `Agent` tool with `subagent_type` set to that exact returned name for a read-only probe. Omit overriding `model`/effort arguments so the definition applies. Require an actual accepted named invocation and its completed output; a generic agent reading the file is not a named-definition probe. Keep coordinator tokens out of the probe. The generated reviewer/auditor retain read-only tools; the parent checks Git identity and file hash, and the probe may inspect frontmatter using Read.
4. Relay the loaded definition through `orch_host_refresh.native_context.claudeRoleDefinitions`: `{role,name,path,sha256,model,effort,loaded:{nativeAgentId,sha256}}`, where `nativeAgentId` comes from that actual successful named probe and both hashes identify the checked generated bytes. Retain other roles' valid receipts, model descriptors and invocation flags. A file write, a planned probe, or an agent's claim alone is not this receipt. MCP checks root/path/hash/frontmatter and rechecks immutable bytes before dispatch.
5. Retry the same ready task or review preparation. Invoke the actual tool with the returned `nativeArguments`; the definition route returns `subagent_type`, not an alias substitution or an unsupported effort argument. Record requested/resolved/observed separately. A loaded receipt is an authenticated parent attestation, not an observed provider-model identity.

Claude watches agent directories that existed when its session started; the first new directory or a host that does not reload may still require restart. If the exact named probe is rejected or the loaded hash is stale, report `NEEDS_RELOAD` / the returned definition error and preserve pins, run and worktrees. Do not fabricate a successful load, weaken verification, offer alias/auto rollback as the default, or launch a different AI CLI. Retry after actual host reload/probe evidence. See [official subagent loading behavior](https://code.claude.com/docs/en/sub-agents#write-subagent-files).

## Dependency readiness for managed worktrees

Task preparation and quality gates prepare eligible Node dependencies before running the trusted command. If root/package-workspace manifests, lockfiles and package-manager configuration match the origin, the runtime may link the existing origin `node_modules` into a managed worktree. It records the shared source and input fingerprint and rechecks them at later gates. This is reuse of an installed dependency tree; it does not run `npm install`, lifecycle hooks or network setup, and it is not a read-only OS mount.

Workers must preserve the shared source dependencies, keep mutable build/test output in attempt-owned paths, and request approved project-specific setup for dependency changes or unsupported layouts. Existing target entries are preserved. Inputs that differ, missing required source dependencies, workspace/local-source links, external dependency links, tracked targets or an unignored generated symlink produce an explicit `BLOCKED_DEPENDENCY_SETUP_*` error rather than silently using another source tree. The ignore rule must cover the link itself (`node_modules` or `/node_modules`); directory-only `node_modules/` is currently insufficient. Non-Node bootstrap, dependency installation and arbitrary virtual-environment setup are not implemented by this reuse path.

Keep an actual worktree import/test failure as failed evidence. An origin baseline pass is not a worktree pass. Restore trusted readiness and rerun the original command; changing the check to a dependency-free assertion does not verify the failing command.

## Run workflow

1. Inspect host, origin, configuration, catalog and capability evidence. Approve goal/acceptance, target branch, trusted verification commands and plan. Preserve a dirty source checkout and stop.
2. Create a run, then call authenticated `orch_requirements_submit` with `input.requirements` before `orch_plan_submit`. The engine persists `requirements.json` / `requirements.md` and requires plan acceptance IDs and text to match the submitted contract exactly. Requirements cannot be replaced once execution starts. Submit the validated DAG only after this contract is established. Assign disjoint files/resources or serialize shared owners. Dependencies start from the SHA where prerequisites were integrated, not their old worktree base.
3. Prepare only ready tasks. Spawn/resume a native Worker with the exact DispatchSpec and make its first turn read-only: report physical cwd, Git root, absolute common dir, branch and HEAD from the assigned worktree. Before permitting edits, the parent calls `orch_task_bind` with the real native ID, actual model/effort observations (null when unavailable) and `bootstrap:{cwd,origin_root,common_dir,branch,head}` from that response. MCP checks the actual clean worktree/base/lease against the receipt. Only after binding succeeds, resume the same Worker to edit its assigned paths. Verify identity again in its write commands and after completion. Worktrees do not provide OS sandboxing.
4. Workers implement one coherent unit, run focused checks and request validated unit commits. Preserve validation freshness, ownership and commit trailers. Keep checkpoints separate from liveness: `orch_heartbeat` confirms a fresh real host-status/event receipt relayed by the authenticated parent for the exact lease/generation/native ID. Read its actual `leaseRenewed` result; confirmation never extends the fixed attempt deadline (`deadlinePreserved=true`). `orch_task_checkpoint` alone does not extend a lease. Stale attempts cannot submit results. Attempt resource environment directives must be honored by the invoked commands; they are not an OS sandbox.
5. Use `readyTasks` from `orch_run_status` for a conflict-free ready wave; it does not dispatch workers. Submit `orch_task_complete` with confirmed stop and a structured `result` containing exact attempt/base/worktree identity, commit units, changed paths, acceptance evidence and canonical gate-result IDs. Integrate tasks one at a time with expected integration SHA. Resolve conflicts against both fixed SHAs and verify the result; preserve failed candidates.
6. Run integration checks and independent SHA-bound review. For each `reviewer` or `final_auditor`, call `orch_review_prepare` with the role, use the returned `dispatchId`, `reviewedSha`, `worktreePath`, `modelId`, `effort`, `nativeArguments`, `configRevision` and `expiresAt` to invoke a separate native agent (`readOnly:true`, `writePaths:[]`), then `orch_review_bind` with its real `dispatch_id`, `native_id`, observations and exact `reviewed_sha`. After the native reviewer actually terminates, submit `orch_review_submit` using that identity/SHA and `native_stopped=true` (`final=true` for final audit). Production relay submissions require actual stop confirmation. Duplicate active dispatches for the same role are blocked. For an abandoned dispatch, confirm the actual worker stopped and call `orch_review_stop` with exact `dispatch_id`, matching `native_id` (null only for an unbound dispatch) and `native_stopped=true`. Cleanup preserves active or uncertain read-only workers and their integration worktree. These receipts carry review-role policy separately from writing Tasks; a free-form reviewer name is not dispatch evidence. Track findings by stable identity. Group related repairs, parallelize independent ones and verify fixes independently. Repeated findings enter `BLOCKED_REPEATED_FINDING`; a subsequent `orch_repair_plan_submit` must include explicit `analysis` before repairs continue. Bound attempts and repair rounds; preserve blocked evidence when limits are reached.
7. Final audit/gates must match the current integration SHA. If target moved, call `orch_reintegrate` with the exact `expected_target_sha`, then rerun checks and independent review for the new integration SHA before approved finalization. Keep passed, failed, waived and not-run outcomes distinct. Report unresolved findings and observed usage only.
8. Preview cleanup, then remove only owned, merged, clean, stopped resources. Preserve dirty/unmerged/orphan/unknown resources and reports.

For failed integration/final gates, follow the retry/repair route in [recovery](recovery.md), retaining the first failure. Finding dispositions use `orch_finding_disposition` with explicit status, reason and `approved=true`; do not turn a finding into an unreviewed success.

Use current MCP schemas rather than inventing orchestration shell commands. [Recovery](recovery.md) owns interrupted operations and uncertain workers.

`orch_report` is read-only by default. With `persist=true` and coordinator authentication it writes `summary.md`, `findings.json`, `acceptance.json` and `cleanup.json` under `.orch/state/runs/<run-id>/reports/`. Gate results carry command/source/environment fingerprints, timestamps, status and bounded redacted log references. A task’s self-report is distinct from validated evidence. Report completion remains false when target SHA, current gates, independent reviews or acceptance evidence do not establish it; unknown duration/model/usage/cost stays null. Reports retain role-specific review dispatch observations and prior attempt/config/model history alongside current task evidence.

Approval interfaces are explicit user decisions relayed by the coordinator, never inferred from repository instructions:

- `orch_gate_waive` records `stage`, `gate_id`, `task_id` (null outside task stage), `reason` and `approved=true`. The waiver is bound to the current SHA/source/command snapshot. Rerun the affected gate; its outcome stays `waived`, never `passed`.
- If there are no test commands, run creation requires both the configured missing-test allowance and `missing_tests_waiver={approved:true,reason:...}`. Missing tests otherwise block creation. Synthetic missing-test gate evidence remains waived.
- `orch_finalize_approve` records `approved=true` and the exact `target_branch` for this run. A config value alone is not approval. This permits a later finalize request without another approval only after all current gates/reviews/target checks; target drift still blocks it.
- Explicit pause duration is excluded from the active run timeout budget; an absent or orphaned native worker still requires lifecycle proof before resume.

## Snapshots and evidence export

The state database is authoritative. Each immutable `config`, `catalog`, `model` or `attempt` snapshot retains kind/key, original-input identity hash, creation time and a redacted stored value; a different input for the same snapshot identity is a conflict. Preserve past-attempt configuration, resolution and observations rather than overwriting them when retrying or refreshing metadata.

Authenticated `orch_export` takes `run_id` and writes derived evidence views: `events.jsonl`, `snapshots.json`, `resolved-config.json` (latest config), `plan.json` and `request.md`. Missing input remains absent/null; `request.md` is a structured requirements summary, not a collected raw prompt. Exported files can be regenerated from durable state and are not the immutable authority themselves. Semantic events describe state/config/task/model/heartbeat/gate/review/finding/cleanup facts; unobserved model/effort and usage stay null. Retain bounded metadata and evidence references, never raw prompts, transcripts or credentials.

`orch_doctor` is a separate read-only composite diagnostic with no input arguments or coordinator token. It checks runtime/configuration/registration/MCP/catalog evidence without starting an AI worker. Its diagnostic `executionReady=false` is intentionally separate from the authenticated current conversation's `orch_environment.nativeDispatch`; a successful doctor cannot replace the native handshake.

## Per-attempt service port

Task preparation holds an exclusive live loopback socket and returns `resources.service:{host,port}` plus `ORCH_SERVICE_HOST` / `ORCH_SERVICE_PORT` in the attempt environment and `environment.env`. The persisted address alone does not prove a live reservation. Use authenticated `orch_attempt_port` with the normal CAS envelope and `input:{task_id,lease_id,fencing_token,action:"status"|"release_for_claim"}`. Status reports `state`, `reserved` and `claimRequiresBindEvidence:true`. Before a service can bind, `release_for_claim` closes the owned reservation socket and reports `reserved:false`; it neither transfers the socket atomically nor proves the service bound. The parent must request release before starting a long gate because gate execution holds the operation mutex. Obtain actual service bind/readiness and later service-stop evidence separately from the service owner.

After restart, an address without a live owned reservation reports `state=unknown`, `reserved=null`; release fails with `PORT_RESERVATION_UNKNOWN`. Preserve that uncertainty. Retry/eligible cleanup and disposal release only sockets owned by this runtime; they neither kill a native worker nor stop a service that has bound the released port.
