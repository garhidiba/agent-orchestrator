# ORCH Configuration Advisor

Keep the current session as coordinator and preserve the active host. Explanation requests produce guidance only; an optimization request authorizes only its stated configuration scope.

For project initialization, follow the main `agent-orch` init route first; configuration explanations stay read-only.

1. Read [configuration](references/configuration.md), [model selection](references/model-selection.md) and [effort](references/reasoning-effort.md). Read [project analysis](references/project-analysis.md) when recommending for a project.
2. Obtain `orch_environment`, `orch_config` with `action=effective`, and `orch_models`. Keep `orch_models.authenticatedNative` separate from subprocess-catalog provenance; check `orch_environment.nativeControl` per-invocation support, context match, access, expiry and errors. For an explicit model edit with missing native metadata, follow [native metadata for configuration](references/model-selection.md#native-metadata-for-configuration) before declaring the edit blocked. Explanation requests stay read-only. Missing or mismatched evidence limits recommendations; never invent IDs, effort support, prices or actual usage.
3. Use the user's goal or explain the `balanced` default. Preserve concrete model/effort overrides and change only `auto` fields unless the user explicitly changes a fixed value. Resolve only within this host's validated catalog. Distinguish a schema-valid patch from a model executable in the current host.
4. For an explicit role/model/effort choice, preview only that authorized change using `orch_config action=patch`, `dry_run=true` and `hashes[scope]` from effective config. Stop for preview/no-write requests; otherwise apply through the same direct interface with that original scope hash, not the dry-run's proposed-file hash. Advisor preserves fixed pins and is not the interface for replacing them at the user's request. For automatic optimization, call `orch_model_recommend action=preview` with the authorized scope and optional profile. If the user's optimization goal has real comparative evidence, supply bounded `assessments` with coordinator authentication even for preview; use only authenticated native candidates with actual invocation support. Retain the returned `expected_hash` and `recommendation_hash` with its validated recommendation, scope, host, config revision/hash, proposed patch, role selections (model, effort, reasons, evidence references, confidence), preserved overrides, warnings and approval requirement. Explain-only requests stop here. Unknown choices remain unresolved; a profile label alone is not a role-model optimization and absent verified default/comparative evidence must not create a new-model patch.
5. Apply an authorized Advisor recommendation through `orch_model_recommend action=apply` with selected scope, the exact preview's `expected_hash`, `recommendation_hash`, unchanged supplied `assessments` and `approved=true`; it recomputes against current metadata/configuration. `CONFIG_CONFLICT` or `RECOMMENDATION_CONFLICT` requires a fresh preview and approval of any changed proposal. Use the actual `orch_config` schema for direct setting patches. Use `unset` to remove an override. For session scope, use `hashes.session`; the applied layer lasts only for this MCP server process and is not a file setting. Use `action=preview` for Advisor previews and `dry_run=true` for direct config previews. Global changes require an explicit global request; never weaken permissions, required review or host boundaries. If the current adapter rejects a model edit, report the rejection and keep the prior settings.
6. Reread effective config and report before/after values and field sources. New settings affect future workers; keep running attempts unchanged. Confirm future dispatch consumes the resolved native model/effort for each role; prompt wording and changing `auto` to `inherit` do not establish application. Report requested/resolved/observed separately, using null for unavailable observations and `NEEDS_RELOAD` when the host requires it. Configuration success does not prove native dispatch support.

Installed `references/` content is generated from the shared release source.
