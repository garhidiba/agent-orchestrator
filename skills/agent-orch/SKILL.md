# ORCH

Keep this conversation as coordinator. Native Agent execution belongs to the host; ORCH MCP owns state, Git, validation and recovery. Use the active host only. Remain in the parent session rather than forking this entire skill.

In Hermes, read [Hermes integration](references/hermes.md) before native connection or execution. `/agent-orch init` uses the same config-only route below.

1. Read [safety](references/safety.md). Call `orch_environment` and verify its `originRoot` matches the physical Git root of the user's client project before any project write. If Hermes returns a null origin, first follow the authenticated one-time project connection in [Hermes integration](references/hermes.md); for any remaining mismatch, stop and reconnect MCP from that project. Read the parent token through `coordinatorTokenRef` only for authenticated MCP calls and keep it private. Route explicit init before native connection or run creation. For other intents in a Git project, call authenticated `orch_project_init` once unless the user requests no writes; a missing file receives full global-plus-default settings and existing files stay unchanged. `installation=READY` means MCP is ready. Execution requests (start/test/resume) with `nativeDispatch=NEEDS_HOST_HANDSHAKE` read [native connection](references/workflow.md#native-connection) and connect this conversation's native Agent tool automatically. Missing native tools or an unsuccessful handshake block execution; preserve state and report the actual error. A separate app-server daemon is not required.
2. Route the intent:
   - Init (`$agent-orch init`, standalone Claude `/agent-orch init`, plugin `/agent-orch:init`): read [project initialization](references/configuration.md#project-initialization). Call authenticated `orch_project_init` with `complete:true`, an optional explicit `profile`, and `dry_run:true` for a preview/no-write request. This writes only the client `.orch/config.yaml`, preserving existing settings/comments and global configuration; it needs no client npm project, run, native handshake or AI worker. Show the full role policies and sources, distinguish unresolved model choices from readiness, and use `agent-orch-configure` only for user-authorized role-model setup with supported current-host metadata. Inspect verification-command candidates without executing or automatically trusting them. Finish after the requested initialization/configuration result; do not fall through to Start.
   - Start: read [project analysis](references/project-analysis.md), [roles](references/agent-roles.md) and [workflow](references/workflow.md). Establish goal, acceptance, ownership, trusted commands and approval before creating a write run. Persist requirements through `orch_requirements_submit` before submitting the plan; plan acceptance must match the saved contract.
   - Diagnosis: use read-only `orch_doctor` for composite runtime/config/MCP/catalog checks; it does not establish native execution.
   - Status/report: use `orch_run_status` / `orch_report` for the user's run ID. Summarize states, SHA-bound gates, findings and unknown observations without changing the run.
   - Resume/pause/cancel/cleanup: read [recovery](references/recovery.md) first; preserve uncertain workers and changes.
   - Models/settings: use `agent-orch-configure` and [configuration](references/configuration.md). Its explicit model-edit route may establish a read-only native metadata connection without starting a run. An explanation request is read-only.
3. Before dispatch, pass the role's prepared model/effort through the actual native tool parameters or verified role definition, including separate read-only reviewer/final-auditor dispatches. When Claude's callable enum or effort parameters cannot express an exact pin, use the [named-definition preparation/probe/refresh route](references/workflow.md#claude-full-model-ids-and-effort-through-named-definitions). Preserve the requested version/effort; an alias/auto rollback is not a repair. An unresolved load requires `NEEDS_RELOAD`, not a fabricated receipt. Managed worktree checks follow [dependency readiness](references/workflow.md#dependency-readiness-for-managed-worktrees); a baseline pass does not prove task readiness. Use the MCP tool's actual input schema. Mutations require coordinator relay, operation ID and current state version where the schema requests them. Treat conflicts as a reason to reread state; retry a known operation with its original ID, not a new mutation.

Necessary managed role-file generation and its exact project-local ignore entries are covered by an authorized execution/test request; do not ask for the same authorization again solely because these runtime assets are new. Actual host permission denials and user-file conflicts remain blocking.
4. Report implemented work, verification evidence, unrun coverage and remaining blockers separately. Finalization requires current target SHA, fresh gates/review and the configured approval policy. Begin cleanup with a dry run.
